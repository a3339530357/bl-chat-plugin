# 长期记忆 V3：阶段 0、1 契约

本次只实现原料保全、状态与提醒，不实现提取 worker、事实/事件写入、清理原料或新 tail 注入。

## 已确认约束

- 未整理原料永久保留，不设置 TTL、不按条数或字节上限裁剪；阈值只提醒。
- 同一 QQ 的事实按群各自存储，所有接口必须带 botId、groupId。
- 后续提取阶段采用充分证据自动入库、歧义待主人确认。本阶段不调用模型。
- 主对话仍使用原连续账本；原料保护不能改变回放正文、模型 header 或注记内容。
- 开发代码位于本仓库，不修改运行副本，不自动部署。

## 配置与生命周期

`memorySource.enabled` 默认 true；`memorySource.groups` 未指定时沿用 `promptCache.groups`，显式 `[]` 表示不选择任何群。群 ID 支持 `*`。这是单独的来源采集选择器，不依赖 `memorySystem.enabled`、提取模型配置、对话开关或当前是否使用 V2 回放。显式关闭来源采集不会删除已保护原料。

默认提醒阈值：10000 条、32 MiB、积压 168 小时，任一达到即可提醒；持久化冷却 24 小时。消息路径每群最多每分钟检查一次，提醒在下一条群消息到来时触发；不增加自动提取或定时全库扫描。

运行时旧 `MemoryManager` 的 `automaticExtraction` 被固定关闭，热更会清除旧提取缓冲和取消旧请求。保留旧查询、删除、清空与召回接口。`#记忆状态` 在旧状态后追加来源积压、保护起点、快照范围及最近错误；来源状态读取失败不覆盖旧状态。

## 数据契约

`utils/memory/sourceSchema.js` 定义 schemaVersion、前缀、作用域编码、来源类型和未来事实/事件的基础枚举。`FACT_SLOTS` 声明单值和按目标多值的区别，但本阶段不实现事实合并。

```text
ytbot:memory:v3:{encodeURIComponent(botId):encodeURIComponent(groupId)}:
  source:seq        STRING：原料自己的单调序号
  source:pending    ZSET：memorySeq → 原始编码记录
  source:seen       HASH：稳定 eventId → memorySeq
  meta              HASH：积压字节、保护起点、错误、提醒冷却
  source:snapshot   HASH：首次历史保全边界、分页和导入进度、缺口
  source:archive    HASH：已捕获的 raw/replay 原编码及近期消息快照
```

键不含账本 resetId，全部不带过期时间。连续模式与账本使用相同 hash tag。按天旧模式的账本 hash tag 含日期；当前支持单实例 Redis，不承诺该模式下可跨键执行 Redis Cluster 脚本。

来源记录包含 eventId、平台消息 ID、QQ、当时昵称、发送和接收时间、完整文本、原消息段、引用消息 ID、@ 对象、内容 hash、来源类型及保真级别。文本优先使用原协议 text 段，不使用 journalContent 或格式化的 200 字预览。不能恢复原文的旧 content 标记为 `legacy_content`，不能假装它是完整证据。

ZSET 外层保存 memorySeq、eventId、ledgerRef 和字符串 payload。这样 Lua 不会把 payload 中的空数组改成空对象。消息有平台 ID 时按 bot/group/messageId 去重；没有平台 ID 的旧历史使用人物、时间、内容与作用域派生 ID，标记为 derived。完全相同且无平台 ID 的旧消息可能无法区分，不能宣称该场景具有平台级去重保证。

四个坐标不可混用：

| 字段 | 含义 |
|---|---|
| 账本 cursor | 对话已消化到的位置，会随账本换代 |
| memorySeq | 同一 bot/group 的来源顺序，不随账本重置 |
| extractedThrough | 已成功整理范围；本阶段初始化为 0，不推进 |
| memoryRevision | 后续有效记忆视图版本；本阶段初始化为 0，不推进 |

## 入账和故障语义

- 有 V2 账本时，来源校验与编码先执行，再在同一个 Lua 调用中写入账本和来源。来源键类型、计数和 JSON 错误必须在写账本前发现。
- 账本已见消息仍尝试补全缺失的来源；重复平台事件不会分配新的 memorySeq。
- RECORD 只给前五个账本键设置 TTL，不使用会覆盖全部 KEYS 的模板给来源键过期。
- 账本不可用或对话退回 V1 时，来源可独立入账；失败的账本写入不会被伪装成成功。记录错误后按来源自身身份补录。
- Redis 不可用时抛出失败、记录日志并在进程内暂存错误；恢复连接后补写错误状态。没有持久本地 WAL，进程同时退出且平台不重投的消息不能保证恢复。
- Lua 不具备异常后自动回滚语义。对预先可检查的错误先校验；基础设施级故障仍受 Redis 自身持久化边界约束。
- `readSourceRange({after, until, limit})` 纯读取，最大每页 64 条。首批返回固定 until，后续传回该 until；新入账消息不会混入这个范围。检测缺失序号并报错，不跨缺口推进。
- 本阶段来源不清理，因此使用 pending 条数、seq、seen 和初始整理游标检查一致性；后续增加提交/异步清理时必须显式升级这个约束，不能直接删 ZSET 行。

## 一次性历史保全

第一次进入选中群的账本记录路径时安排后台快照，主消息不等待快照完成。已有近期缓冲作为快照输入；后台按最多 64 条复制一页 raw 或 replay，页间让出事件循环。采集任务不占对话并发计数，也不调用 `ContextStore.read()`。

快照保存 resetId、原 raw 范围、回放数量与回放修订号。raw 被并发提交回收、scope 切换、回放变更时标记 partial/gap；已经捕获的数据仍保留并导入。新数据持续正常采集，旧快照只尝试一次固定边界，不把完整历史恢复作为保全成功前提。

先归档再导入：已捕获 raw 与近期结构化消息进入待整理区，按稳定 ID 去重；导入进度持久保存。重启后在该群下一次入账时恢复尚未结束的保全。replay 逐块原样存入 archive，本阶段不反解析它的人物或日期，也不把机器人/工具投影当成真实群友发言。

近期缓冲快照超过 4 MiB 时明确报错，不静默截断；快照解析在后台。平台消息本身未设截断上限，分页限制的是消息/块数量，不是任意单条消息的字节大小。
